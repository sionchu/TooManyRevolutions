## 1. Mission

Design the smallest two-domain architecture that can later represent:

1. **Rebellion operational persistence** — why an already-created rebellion can continue as an identified operational episode even with zero faction-controlled LandHexes and no current derived front; and
2. **Rebellion settlement / demobilization / suppression closure** — what explicit authoritative process can prove that the rebellion has ended or lost the capacity to continue.

The domains must remain separate from:

- T018 political eligibility;
- T021 territorial projection and `LandHex.controller` mutation;
- T022 Order Consolidation;
- T023 State Dissolution;
- generic Faction/Country pressure scalars;
- derived Agenda/read-model state.

This is **docs-only schema/architecture design**. Do not implement production state, actions, events, persistence V8, scenario content, or tests in FIX21.

## 2. Required design outcome

Specify both domains precisely enough that a later implementation task can begin without inventing semantics.

### A. Rebellion Persistence domain

Design the minimum scenario-owned authoring concepts and future authoritative runtime concepts needed to distinguish:

```text
active rebellion Conflict identity
+ explicit operational persistence evidence
!= territorial front
!= generic faction grievance/organization/resources
```

The design must answer:

- what static authoring is needed, if any;
- what the conflict-scoped runtime identity/state is;
- what bootstrap event creates the persistence episode when T018 creates the rebellion;
- what kinds of typed operational evidence may keep/change that episode;
- what kinds of evidence may establish operational collapse;
- how zero LandHex / no front is represented without becoming either persistence proof or defeat proof;
- what is authoritative versus derived;
- what future action/event provenance is required;
- what must be serialized if/when the runtime seam is implemented.

Do **not** solve this with a numeric insurgency/strength/persistence score, hidden threshold, automatic decay, timer, or pre-authored end result.

### B. Settlement / Demobilization domain

Design a separate minimal lifecycle that can distinguish at least:

```text
proposal / opening
negotiation or bargaining state
acceptance
implementation
compliance or breach
suppression or demobilization evidence
closure eligibility
```

The exact lifecycle may be smaller if justified, but acceptance alone must not equal completed peace. The design must answer:

- party identity and conflict identity;
- static authored package/term identity, if needed;
- how terms are represented without unstructured narrative authority;
- how player/heuristic/LLM may propose only schema-valid actions;
- how implementation/compliance is proven;
- how settlement closure differs from military/operational collapse;
- how the existing `applyConflictOutcome()` / typed Conflict outcome boundary should or should not be reused;
- how existing Intervention Catalog / Political Proposal concepts may be referenced without silently reinterpreting their current semantics;
- what future runtime state and persistence would be required.

Do not directly delete a Conflict or schedule peace by story/timer.

## 5. Required proof obligations

### Persistence bootstrap

T018 creates an active rebellion because political/crisis prerequisites are met. Explain how a future persistence episode can be bootstrapped without simply asserting `persistence = true because rebellion exists`. If the start event itself is legitimate operational evidence, state exactly why and what authored capability/fact it instantiates.

### Positive persistence evidence

Define what counts as positive evidence of continued operational capacity. “Still active,” no-front observations, faction grievance, or elapsed time are not positive evidence.

### Collapse evidence

Define what can prove loss of capacity without a generic score or `0 LandHex` shortcut. If explicit suppression/demobilization action is required, place it in the correct domain.

### Territory independence

Preserve:

```text
LandHex.controller = sole physical territorial authority
fronts = derived
persistence != territory
```

No new domain may mutate LandHex except via the existing territorial authority path.

### Settlement implementation

Acceptance must not directly resolve the rebellion unless the selected minimal lifecycle explicitly proves completion. Explain how implementation/compliance/demobilization reaches typed closure.

### Same-conflict coexistence

Explain whether a rebellion may simultaneously have:

- active persistence state;
- territorial control/fronts;
- an open settlement process.

The design must avoid mutually inconsistent authoritative writers.

### Replay/determinism

Specify how future authoritative state changes will be backed by ActionRecord + GameEvent provenance and how save/load replay remains deterministic.

### Player/AI/LLM boundary

LLM/heuristic may choose only among schema-valid actions grounded in authoritative decision context. No direct mutation and no invented terms/evidence.

### No pacing cheat

The design must remain defensible even if it does not reduce the historical 1200-day silence immediately.
